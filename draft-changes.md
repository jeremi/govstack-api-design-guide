# Draft changes

## 0.3.0-draft, 2026-10-29

This unpublished revision corrects the guide and linter after the registries, scheduler, and payments reviews. Scheduler requirement migration (D3) and its paired parser work (L14) remain deferred.

- [§1.2](1-introduction.md#12-scope) distinguishes BB-provided interfaces from standalone counterparty contracts without exempting the callbacks and webhooks already governed by §15.8 and §16. [§1.10](1-introduction.md#110-applicability-and-transition) defines publication for transition purposes as the default-branch contract or a released specification. (Scope clarification.)
- [§7.14](part-b/7-http-status-codes.md#714-all-status-codes-declared) keeps required status codes explicit and limits `default` to fallback errors. [§11.1](part-c/11-errors.md#111-rfc-9457-problem-details) requires error content where HTTP permits it and exempts HEAD; its error statuses remain declared. (Clarification of error contracts.)
- [§9.7](part-c/9-json-conventions-and-naming.md#97-screaming-snake-case-enum-values) makes enum casing a SHOULD, with externally fixed values retained as scope exclusions; the casing proxy reports info. [§9.9](part-c/9-json-conventions-and-naming.md#99-no-closed-enums-for-growing-sets) permits closed request-only selection vocabularies while retaining tolerant-reader obligations for schemas also emitted in responses or events. (Relaxations.)
- [§11.2](part-c/11-errors.md#112-stable-http-problem-type-uri) distinguishes failure of the current HTTP request from a failed business process reported by a successful lookup or acknowledged callback. (Clarification.)
- [§18.5](part-d/18-compatibility-and-lifecycle.md#185-deprecation-and-sunset-headers) keeps incompatible security corrections versioned and leaves urgent retirement decisions with the responsible authority under GovStack governance; an unsafe endpoint need not remain available until a replacement exists. (Governance boundary clarification.)
- [§19.1](part-e/19-localisation.md#191-honour-the-request-language) explains the declared fallback for a single-language deployment, retaining response-language metadata. [§20.3](part-e/20-conformance-and-validation.md#203-declared-guide-conformance-version) distinguishes security declarations under §13.1 from security schemes under §13.2 to §13.6. (Clarifications.)
- The linter attributes referenced-schema findings to their source and deduplicates them, preserves scoped exceptions through reference chains and all supporting approval records, keeps every finding in JSON, and names the number of locations omitted from grouped text. Repository scans report malformed API candidates, while explicit-file runs omit unrelated inventory checks. Missing coverage diagnostics cite §4.6; requirement parsing is unchanged. (Tooling.)
- The §14.1 proxy covers POSTs returning `201` or `202` and also represents §8.3, avoiding duplicate idempotency-key findings. Date-name and strict identifier heuristics follow the reviewed payment cases, and body-example messages use SHOULD wording. The §2.6 URL-version check only rejects an actual repeated path version and is separately advisory under legacy. The §20.1 schema-type check supplements the mandatory base validators. (Tooling.)
- The §12 pagination proxy exempts an explicitly declared single-object result unless it carries collection or pagination signals, so a lookup containing an embedded list is not forced into a Page envelope. Bare arrays, `items` envelopes, and declared pagination controls retain their checks. (Tooling.)
- Independent-review follow-up: [§7.2](part-b/7-http-status-codes.md#72-201-created-with-location) requires both mechanical checks and semantic review, with creation semantics explicitly reviewed rather than inferred from operation names; its MUST obligations are unchanged. Coverage for §7.2, §7.3 and §15.1 is partial. Location and success-schema checks cover paths, webhooks and nested callbacks. The §15.1 check requires concrete content schemas on `202` responses except HEAD, which cannot declare content; it owns those findings to avoid duplicates with §7.21. The latter also prohibits content on HEAD, `204` and `205` responses. (Enforcement correction and coverage clarification.)
- [§16.4](part-d/16-cloudevents-and-webhooks.md#164-stable-cloudevents-source) identifies the occurrence context and permits stable authority, tenant, deployment and environment identities. Shared-source producers preserve `source` plus `id` uniqueness. OpenAPI and AsyncAPI checks validate pinned/example lexical shape; stability and provenance remain review obligations. (Relaxation and alignment with CloudEvents 1.0.2.)
- [§10.6](part-c/10-data-types-and-formats.md#106-rfc-5322-email-addresses) names the RFC 5321 Mailbox syntax used by JSON Schema's `email` format; the existing anchor is preserved. Quick-start commands now list pinned base-validator installation for each applicable surface and explain that `npm ci` installs only the linter. (Standards citation and adoption corrections.)
- [§5.9](part-b/5-url-structure-and-versioning.md#59-unversioned-health-endpoint) is an informative reference to `govstack-cfr-architecture#req-15`; its four health-specific linter checks are retired. The existing anchor and §5.10 exemptions for optional `/health` and `/ready` endpoints remain. (Removal of guide-specific health requirements.)
- The §5.4 check treats fixed identifiers supported by matching Digital Registries collection metadata like parameterized identifiers, preserving genuine revision-depth warnings. The §10.2 proxy accepts explicit calendar dates on `At` fields and checks composed temporal schemas and resolved references; timestamp values still require uppercase UTC `Z` under the unchanged prose. (False-positive corrections.)
- Visible enforcement-class badges are replaced by verification details generated from the linter coverage manifest. Legacy classes remain hidden compatibility metadata; rule identifiers, anchors, normative levels, and linter behavior are preserved. [§1.9](1-introduction.md#19-rule-enforcement-classes) explains the verification methods and their limits. (Presentation.)

## 0.3.0-draft, 2026-10-22

This unpublished revision is the first to use the amended [§1.10](1-introduction.md#110-applicability-and-transition) policy: during the `0.x` series a minor release may add or strengthen a requirement when this record lists it. Two reviews drove it: (a) a census of the published BB API specifications, summarised in the [current practice census](appendix/current-practice-census.md) appendix, and (b) a review of the TM Forum alignment proposal.

- [§1.10](1-introduction.md#110-applicability-and-transition) is amended: a `0.x` minor release may add or strengthen a requirement when this record lists the change with its rationale and rule ids; from `1.0.0` the same change needs a major release. (Process strengthening.)
- [§4.7 Operation metadata extensions](part-a/4-documentation-requirements.md#47-operation-metadata-extensions), a new [M+R] rule, defines the optional `x-govstack-use-case` and `x-govstack-pii` operation extensions with a fixed shape when present. On new surfaces they replace ad hoc `x-specification-*` names. (Optional addition.)
- [§5.10](part-b/5-url-structure-and-versioning.md#510-standard-unversioned-endpoints) also exempts its endpoints from [§5.2](part-b/5-url-structure-and-versioning.md#52-plural-noun-resources), so a well-known URI such as `/.well-known/api-catalog` keeps the spelling RFC 8615 and its registry give it. (Relaxation.)
- [§5.3](part-b/5-url-structure-and-versioning.md#53-kebab-case-path-segments), [§5.4](part-b/5-url-structure-and-versioning.md#54-shallow-path-nesting), [§5.8](part-b/5-url-structure-and-versioning.md#58-actions-as-sub-resources), [§6.6](part-b/6-http-methods.md#66-post-search-for-complex-queries), and [§12.9](part-c/12-pagination-filtering-sorting.md#129-complex-filtering-via-search) withdraw the colon custom methods added in `0.2.0-draft`: action sub-resources such as `POST /v1/events/search` and `POST /v1/events/{eventId}/cancel` are the single convention; §5.4 no longer exempts an operation suffix from the nesting count, so an action sub-resource counts as a level. §5.8 becomes a MUST rule: a non-CRUD operation is an action sub-resource and does not use a colon custom method, and an action name used on a collection **MUST NOT** be a valid identifier in that collection, because OpenAPI matches a concrete path such as `/v1/events/search` before a templated one such as `/v1/events/{eventId}`. The identifier format excludes the reserved names, or the specification states that they are reserved. (Withdrawal of an unpublished addition; strengthening of §5.8 from SHOULD to MUST.)
- [§7.2](part-b/7-http-status-codes.md#72-201-created-with-location) and [§15.1](part-d/15-asynchronous-operations.md#151-202-with-operation-location) clarify that creating a job resource that is addressable when the response returns is a completed creation (`201`); `202` applies only when nothing addressable exists yet. (Clarification; obligations unchanged.)
- [§8.8 Custom header naming and placement](part-b/8-headers.md#88-custom-header-naming-and-placement), a new [M+R] SHOULD rule, recommends the `GovStack-` prefix for cross-BB headers and plain names for BB-local headers, and keeps business identifiers, tenant identifiers, callback URLs, and personal data out of custom headers. (Strengthening, SHOULD.)
- [§9.7](part-c/9-json-conventions-and-naming.md#97-screaming-snake-case-enum-values) lists §12.10 field-selection names, which are property names, among the values that keep their own casing. (Clarification.)
- [§9.10](part-c/9-json-conventions-and-naming.md#910-govstack-extension-prefix) cites the §4.7 extensions as examples. (Editorial.)
- [§11.2](part-c/11-errors.md#112-stable-http-problem-type-uri) permits an optional `code` member that mirrors a documented BB or external machine code; `type` remains the problem identifier and `timestamp` remains forbidden. (Relaxation.)
- [§11.3](part-c/11-errors.md#113-trace-identifier) permits a legacy `requestId` or `correlationId` member beside `traceId` on an existing surface. (Relaxation.)
- [§12.5](part-c/12-pagination-filtering-sorting.md#125-optional-total-count) and [§12.6](part-c/12-pagination-filtering-sorting.md#126-offset-pagination-envelope) make `total` optional in the offset envelope too, and permit offset pagination wherever the backing source supports stable offsets, with one pagination contract per operation. (Relaxation.)
- [§12.9](part-c/12-pagination-filtering-sorting.md#129-complex-filtering-via-search) follows the operation's chosen pagination contract: a body-based search carries `pageSize` and `cursor`, or `offset` and `limit` under §12.6, in the request body and responds with the matching §12.3 or §12.6 envelope. Under offset pagination, each subsequent page request repeats the criteria and sort values of the first. (Relaxation, aligning §12.9 with §12.6.)
- [§12.10 Response field selection](part-c/12-pagination-filtering-sorting.md#1210-sparse-fieldsets-out-of-scope) is now an [M+R] rule: the `fields` query parameter is reserved and has a fixed shape where offered; support remains optional. The anchor is unchanged. (Addition with a reserved name.)
- [§12.10](part-c/12-pagination-filtering-sorting.md#1210-sparse-fieldsets-out-of-scope) covers enveloped representations: where identifiers and source metadata sit apart from a single payload member, the selectable names are that member's top-level property names, the API documents which member is selectable, and the envelope members are always returned. (Clarification.)
- [§13.3](part-d/13-authentication-and-authorisation.md#133-distinct-scheme-for-bb-to-bb-calls) recommends referencing the shared Information Mediator security scheme and client-identification header once the shared component library publishes them. (Conditional SHOULD.)
- [§15.8 Per-request callback URL](part-d/15-asynchronous-operations.md#158-per-request-callback-url), a new [M+R] rule, fixes the shape of a per-request callback when an operation offers one: a `callbackUrl` body property, `https`, an OpenAPI `callbacks` object, and never a header or query parameter. (Addition; MUST shape when the pattern is used.)
- [§16.9](part-d/16-cloudevents-and-webhooks.md#169-readiness-for-a-shared-signature-profile) is marked informative explicitly. (Editorial.)
- [§18.1](part-d/18-compatibility-and-lifecycle.md#181-semver-versioning) states that the CFR specification-document version and `info.version` are independent, and that a specification release should record the `info.version` it ships. (Clarification and SHOULD.)
- [§20.3](part-e/20-conformance-and-validation.md#203-declared-guide-conformance-version) adds an optional `profile` member (`standard` or `legacy`). The linter ships a legacy profile that reports wire-contract rules at informational severity for surfaces published before the guide and still on the same major version. (Addition.)
- The linter adds rules for §4.7, §12.10, and §15.8, and a strict-only rule for §8.8; its §11.2 and §12.6 rules follow the relaxations above. A `--profile` flag selects the `legacy.yaml` profile. (Tooling.)
- The linter's §5.3 rule flags a colon custom method and points to §5.8 action sub-resources; its §6.6 and §12.9 rules recognise the `/search` and `/lookup` sub-resources; its §12.9 rules accept an `offset`/`limit` body with the §12.6 envelope and flag a body/envelope mismatch; and the strict §5.2 rule accepts `search` and `lookup` as the final path segment. Reserving action names from identifier formats is review-only; the §4.1, §4.2, §9.7, and §9.9 rules do not descend into `not` subschemas, so an exclusion such as `not: { enum: [lookup, search] }` is not read as an undocumented or mis-cased enum. (Tooling.)
- The linter's §12.10 rule also accepts `fields` as a string array with `style: form` and `explode: false`, which serialises as the same comma-separated list; its §7.13 and §7.14 rules check every operation method, including `HEAD`; the strict §5.2 rule skips the §5.10 endpoints; and its §9.7 rule skips sort-key and field-selection enums. (Tooling.)
- The informative [Current practice census](appendix/current-practice-census.md) appendix records the census findings and the guide's departures from current practice. (Informative.)

Reviewed, not adopted, from the TM Forum alignment proposal:

- camelCase path segments: [§5.3](part-b/5-url-structure-and-versioning.md#53-kebab-case-path-segments) keeps kebab-case as a SHOULD. TM Forum uses camelCase, but kebab-case is the common web practice and the current drafts already use it.
- Bare array responses with HTTP pagination headers and `206`: the guide keeps body envelopes and `200`, because RFC 9110 §15.3.7 reserves `206` for range requests.
- Mandatory `id` and `href` on every resource: the guide keeps the local identifier model of [§10.1](part-c/10-data-types-and-formats.md#101-opaque-server-generated-identifiers), with no duplicate aliases and no self-link on embedded values.
- The TM Forum Error representation: the guide keeps RFC 9457 Problem Details ([§11](part-c/11-errors.md)), now with the optional `code` member.
- The TM Forum event and subscription model: the guide keeps CloudEvents in structured content mode ([§16](part-d/16-cloudevents-and-webhooks.md)).

## 0.2.0-draft, 2026-09-17

This unpublished revision applies the guide and linter to a registry consultation contract and its example deployments:

- [§8.7](part-b/8-headers.md#87-rate-limit-headers-declared) keeps quota-scope documentation, gateway-ownership statements, `Retry-After` on `429`, `RateLimit-Policy` for advertised policy details, and the caution about legacy fields as SHOULD. Declaring the advisory `RateLimit` header becomes MAY, matching its Internet-Draft status. [§7.12](part-b/7-http-status-codes.md#712-429-for-rate-limits) refers to `Retry-After` instead of every §8.7 header. The linter's §8.7 proxy checks only `Retry-After` on declared `429` responses.
- [§7.16](part-b/7-http-status-codes.md#716-etag-and-if-none-match) recommends `ETag` for single resources; collection responses and pages MAY advertise one. The linter proxy skips GETs whose `200` body is an array or an `items` page.
- [§2.3, §3.3](part-a/2-openapi-document-standards.md#23-no-divergent-openapi-copies), and [§20.1–§20.3](part-e/20-conformance-and-validation.md) treat operation-bearing documents under `api/examples/` as example contracts. They are not canonical surfaces, divergent copies, or coverage evidence, but they pass the base validators, declare the guide version, and pass the Spectral ruleset. This is an explicit addition to the same unpublished `0.2.0-draft`. The driver lints example contracts by default and skips them when `--openapi` or `--asyncapi` names the files to lint.
- The §4.1 linter proxy no longer asks for a description on a combinator-branch property that narrows a described property of the enclosing object, such as a `const` selector in a `oneOf` branch.
- [§12.8](part-c/12-pagination-filtering-sorting.md#128-simple-equality-filtering) keeps `pageSize`, `cursor`, and `sort` for pagination and sorting: a field with one of those names uses another documented filter parameter name. The rule level is unchanged.

## 0.2.0-draft, 2026-09-09

This revision simplifies the guide after applying it to a registry consultation API. It changes how rules are expressed, lowers the level of twenty-one review-assessed rules, and adds no mandatory requirement, so the exact version stays `0.2.0-draft` under [§1.10](1-introduction.md#110-applicability-and-transition).

- [§1.5](1-introduction.md#15-language) fixes one level per rule: the first paragraph of a rule body uses one RFC 2119 family and later paragraphs only weaker ones. Every rule body was reordered or split to follow the convention without changing keyword strengths, except for the demotions below. `rules.yaml` now records `level` and `kinds` for each rule instead of the `strengths` list; `rules.yaml` and the ruleset are named as the reference expressions of the rules, with prose as rationale.
- [§1.11](1-introduction.md#111-which-rules-apply-to-your-api) and the generated [Rules by API kind](rules-by-kind.md) page assign each rule to read-only HTTP APIs, HTTP APIs with mutations, event surfaces, or the deployment profile. The deployment profile holds runtime obligations: [§6.3](part-b/6-http-methods.md#63-put-replaces-the-entire-resource), [§11.5](part-c/11-errors.md#115-stable-http-problem-fields-across-languages), [§14.2](part-d/14-idempotency.md#142-opaque-client-generated-keys), [§14.4](part-d/14-idempotency.md#144-replay-returns-original-response), [§14.5](part-d/14-idempotency.md#145-key-reuse-and-fingerprint-mismatch), [§16.7](part-d/16-cloudevents-and-webhooks.md#167-replay-detectable-signed-material), [§19.1](part-e/19-localisation.md#191-honour-the-request-language), [§19.2](part-e/19-localisation.md#192-never-translate-stable-content). §14.2 also appears on the HTTP specification checklists because it requires key-syntax and length documentation. §19.3 remains on the HTTP and event specification checklists because it requires a declared default language; §19.4 covers response-language declarations on both surfaces.
- Review-assessed rules that restate HTTP semantics or documentation duties move from MUST to SHOULD: [§6.2](part-b/6-http-methods.md#62-post-creates-or-performs-actions), [§7.1](part-b/7-http-status-codes.md#71-200-for-successful-reads), [§7.4](part-b/7-http-status-codes.md#74-204-for-void-responses), [§7.9](part-b/7-http-status-codes.md#79-409-for-state-conflicts), [§7.10](part-b/7-http-status-codes.md#710-410-for-permanent-removal), [§7.11](part-b/7-http-status-codes.md#711-422-for-semantic-errors), [§7.12](part-b/7-http-status-codes.md#712-429-for-rate-limits), [§7.15](part-b/7-http-status-codes.md#715-412-for-failed-preconditions), [§8.7](part-b/8-headers.md#87-rate-limit-headers-declared), [§14.3](part-d/14-idempotency.md#143-documented-replay-window), [§14.6](part-d/14-idempotency.md#146-naturally-idempotent-designs), [§15.2](part-d/15-asynchronous-operations.md#152-local-operation-resource-shape), [§15.3](part-d/15-asynchronous-operations.md#153-documented-operation-lifecycle), [§15.7](part-d/15-asynchronous-operations.md#157-documented-result-retention), [§16.10](part-d/16-cloudevents-and-webhooks.md#1610-documented-delivery-failure-contract), [§17.11](part-d/17-asyncapi-channel-rules.md#1711-duplicate-delivery-contract), [§17.12](part-d/17-asyncapi-channel-rules.md#1712-ordering-only-when-promised), [§17.13](part-d/17-asyncapi-channel-rules.md#1713-public-delivery-management-capabilities), [§17.14](part-d/17-asyncapi-channel-rules.md#1714-implementation-values-in-protocol-profiles), [§17.15](part-d/17-asyncapi-channel-rules.md#1715-no-universal-delivery-extensions), and [§17.18](part-d/17-asyncapi-channel-rules.md#1718-correlated-completion-signals). The linter proxies for §8.7 drop one severity notch to match; the other demoted rules have no Spectral rule.
- [§7.16](part-b/7-http-status-codes.md#716-etag-and-if-none-match) is a SHOULD-level rule about advertising `ETag`; its strong-validator requirement moves into [§7.17](part-b/7-http-status-codes.md#717-optimistic-concurrency-with-if-match), which now states the conditional MUST for endpoints that support optimistic concurrency (strong `If-Match`, `412` rather than `409`) and keeps support itself and `428` as SHOULD.
- [§9.10](part-c/9-json-conventions-and-naming.md#910-govstack-extension-prefix) offers `x-govstack-{bb-code}`, a published JSON Schema, and a BB requirement citation as optional conventions for BB-owned extensions. The existing requirement for an explicit schema and governing rule remains; this draft adds no mandatory naming or publication constraint. [§5.10](part-b/5-url-structure-and-versioning.md#510-standard-unversioned-endpoints) names the RFC 9727 API catalog as a well-known URI and treats the static documents it links to as published content outside the business surface. [§9.1](part-c/9-json-conventions-and-naming.md#91-json-as-default-media-type) admits media types fixed by the standard that defines a document, such as `application/linkset+json` and `application/ld+json`. [§4.6](part-a/4-documentation-requirements.md#46-functional-requirement-traceability) notes that a DRAFT requirement's body states its intended level.
- [How to use this guide](how-to-use-this-guide.md#what-a-bb-publishes) now leads with the four artifacts a BB publishes and the single linter command, and [§1.10](1-introduction.md#110-applicability-and-transition) records the intended yearly release cadence with BBs re-pinning at their next specification version.

## 0.2.0-draft, 2026-09-06

Guide and ruleset `0.2.0-draft` refine the unpublished `0.1.0-draft` after applying it to an adapter-oriented read API. These are cross-BB relaxations and clarifications: existing wire contracts remain supported, while a specification opting into this revision pins the new exact guide and ruleset versions. The minor increment preserves the version policy in [§1.10](1-introduction.md#110-applicability-and-transition); it is not a publication or ratification claim.

- [§10.1](part-c/10-data-types-and-formats.md#101-opaque-server-generated-identifiers) permits stable source-owned identifiers and explicitly scoped uniqueness. New UUIDs and a mapping service are not required merely to expose an existing resource. Personal-data restrictions in URLs remain unchanged.
- [§9.8](part-c/9-json-conventions-and-naming.md#98-forward-compatible-schemas) distinguishes extensible response resources from operation request schemas that reject unknown inputs. The linter now permits closed request bodies while retaining its response-root check.
- [§6.6](part-b/6-http-methods.md#66-post-search-for-complex-queries) expressly permits body-based exact lookup as well as collection search. A single-resource lookup does not require pagination or an idempotency key merely because it uses POST.
- [§2.6 and §5.1–§5.2](part-b/5-url-structure-and-versioning.md#51-major-version-in-the-path) clarify version placement before the resource hierarchy, with an optional deployment routing prefix. One API can expose multiple typed collections and capabilities; API-family names do not require URL prefixes. Independently exposed API contracts can version separately.
- [§5.3 and §5.8](part-b/5-url-structure-and-versioning.md#58-actions-as-sub-resources) permit colon custom methods alongside action sub-resources, with kebab-case resource segments and camelCase method suffixes. [§6.6](part-b/6-http-methods.md#66-post-search-for-complex-queries) and [§12.9](part-c/12-pagination-filtering-sorting.md#129-complex-filtering-via-search) apply the same read and pagination semantics to either spelling. This explicit addition to the same unpublished `0.2.0-draft` supports operation routes that coexist with opaque identifiers such as `search`; existing sub-resource contracts remain supported. The linter recognises custom-method syntax and offers advisory checks for conventional Search and Lookup names; operation semantics and route collisions remain review concerns.
- [§12.2–§12.3](part-c/12-pagination-filtering-sorting.md#122-cursor-pagination-by-default) permit an explicitly documented fixed page size and explain continuation through short or empty pages. The existing Page envelope, repeated criteria, cursor protection, and optional totals remain. A cursor does not promise snapshot consistency or another matching item.
- [§12.1](part-c/12-pagination-filtering-sorting.md#121-collections-must-paginate) clarifies that a single resource can contain subobjects and schema-bounded embedded arrays without additional Page envelopes. A bounded complete view can fail explicitly on overflow; offered traversal beyond its bound uses documented pagination. The representation distinguishes completeness for a permitted view from selected or partial data. Bounds belong to the applicable schema or profile, and JSON nesting is independent of URL depth. These are explicit additions to the same unpublished `0.2.0-draft` revision; nested bounds and completeness remain semantic review concerns.
- [§10](part-c/10-data-types-and-formats.md) clarifies the boundary between common API fields and separately governed domain schemas. Domain ownership does not silently waive inherited CFR requirements, including UTC timestamps and UTF-8.
- [§2.3 and §3.3](part-a/2-openapi-document-standards.md#23-no-divergent-openapi-copies) allow clearly documented historical contracts under `api/legacy/`. The driver excludes that archive from current-surface discovery while still validating any explicitly declared or referenced artifact.
- [§4.6](part-a/4-documentation-requirements.md#46-functional-requirement-traceability) permits an empty active coverage array and a separate optional `draftRequirements` array. Contract validation does not require premature promotion of draft requirements. Active obligations retain exact coverage checks; draft references are checked against DRAFT markers and reported as design traceability rather than certification.

The shared schema artifacts remain at their separately pinned `0.1.0-draft` versions. Their shapes already support these contracts and this guide change does not alter their upstream provenance. Linter validation also uses a compatible CommonJS import for its existing Spectral runtime dependency; no dependency versions change.
